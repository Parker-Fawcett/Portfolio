Visible Tests Are Not a Specification.

A coding agent passed a page test on a todo app. The rebuilt page could not manage todos. The test had checked for three strings and nothing more.

Parker FawcettSeptember 2026~6 min read

It is tempting to read a green test suite as a statement about the software. In an agentic rebuild, that shortcut can be especially persuasive: the agent had a specification, it wrote code, the checks passed, and a report says the job is done. But the test suite may be describing only what the test harness happened to observe.

One Rebuild Dossier experiment made that gap unusually clear. I ran the tool against a small, independently authored todo application, then gave a coding agent the generated specification without access to the original source. The visible page test passed. The resulting interface was a static shell.

The todo app that passed without todos

The original application had an interactive todo list and CRUD behavior. The generated page test, however, asserted only that three fixed strings appeared in the rendered page. It did not add a todo, change one, delete one, or check that the interface was wired to the API. A page containing those three strings could pass.

That is what the blind rebuild produced: a noninteractive shell that satisfied the visible page check. The agent also built GET, POST, PUT, and DELETE endpoints in a batch, but that extra work did not make the page a working todo interface. The result was a valid pass against the test we had written and a poor match for the feature a person would recognize. The paper records this as a narrowness error in the verification signal, alongside separate findings about the agent’s build process. See §4.7 and §5.1 of the technical report.

A broader check made the gap measurable

The todo run is a concrete example, not a prevalence estimate. A later evaluation asked a broader question: how much of an application’s original behavior survived when the generated tests said the rebuild was complete? In a September 27 entry in the project’s chronological findings log, I reported an author-written requirements check against 30 archived rebuilds of one application. Every run had completed the visible suite. Against the original app’s behavior that could be checked without its database, weak-tier rebuilds matched 18 of 960 checks (1.9%); strong-tier rebuilds matched 176 of 480 (36.7%).

Those percentages describe this one app and this particular check, not coding agents generally. The check was written by the author, covered only behavior decidable without the database, and compared response keys coarsely. Its value here is the direct comparison: visible test completion and behavioral fidelity gave very different answers on the same archived runs. The frozen check and run evidence are available in the repository.

How a measurement becomes a requirement

A generated test starts as a measurement of an existing app. During a rebuild, it becomes an instruction: make this test pass. If the measurement captured only visible text, the agent has no reason to infer every interaction that text was attached to. It may build exactly the narrow behavior the test rewards.

The same project surfaced a different version of that problem with an animated counter. A capture taken before the animation settled recorded an intermediate value. A blind rebuild hardcoded that intermediate value as permanent content and passed the available checks, while reproducing none of the animation. In that case the harness recorded the wrong moment; in the todo case it recorded too little behavior. The capture bug was later fixed with DOM-text-stability polling, as the findings log records. Both experiments show how the evidence supplied to an agent can shape the result. The report separates the failure mechanisms in §5.1 and Appendix C.5.

Even a held-out test can give away its answer

A later experiment found another weak boundary. The held-out contract did not include a page’s required text, but a failing test printed that text in its assertion output. An agent could rerun the held-out suite against a wrong implementation and read the expected string without opening the test file. The paper reports that, in one ten-run batch, the reps that repeatedly ran held-out tests went green while the two that ran them once failed with placeholder content. That association does not establish what caused every earlier result, and the paper says so. It does identify a leakage path that was reproduced directly. See §4.14 of the report.

The fix was to put the captured static text into the legitimate page contract, so the withheld assertion was no longer the only place an agent could learn it. In the repeat batch after that change, all eight valid runs passed held-out regardless of how often they reran it. The larger point is that “held out” describes an intended boundary; the test runner’s output is part of that boundary too.

What I would check before trusting green

These are small experiments, and the third-party todo result is one application, one model tier, and one run. It is a demonstrated failure mode, not a measured failure rate. The practical response is to ask what each check actually proves:

  1. Name the user action. If a feature is “manage todos,” check a create, update, and delete path, not just the labels around them.
  2. Audit the capture. A screenshot or DOM snapshot can freeze a transient state. Verify when it was taken and whether the value is supposed to change.
  3. Inspect the test boundary. A withheld file can still expose expected values through failure output. Check what the agent can run and read during the build.
  4. Separate process from outcome. An agent can follow its build rules and still implement an incomplete test; it can also pass a test after violating a build rule. Record both claims independently.
  5. Compare against the original system. Run the same meaningful interaction against both applications when possible. A green generated suite is one piece of evidence, not the definition of equivalence.

Rebuild Dossier tries to lock interface contracts and expose weak tests before an agent starts. That helped in some targeted checks, but the project’s own evaluation found places where the contract or test still missed behavior. The useful lesson is narrower than “tests do not work.” Tests work for the behaviors they express. The hard part is proving that those behaviors are the ones the user needs.
